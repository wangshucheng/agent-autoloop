# 00 总纲：super-agent-auto-loop-runtime 架构设计

> 版本：设计稿 v1.0 · 2026-11-05 · 面向 master（高见远）
> 输入：`agent-autoloop`（底座）+ `dsh-superagent-prototype`（设计思想与源码）
> 目标平台：macOS 生产，WSL 开发

---

## 0. 先回答三个最容易跑偏的问题

### 0.1 能否支持主会话 LLM 评估？

**能，而且必须做成「旁路订阅 + 事实回写」，不能把 LLM 塞进内核。**

`agent-autoloop` 的内核有一个非常硬的约束（`kernel/decide.ts`、`SECURITY.md`、`docs/protocol.md`）：

- 不读系统时钟、不取随机数、不向外发请求；
- `decide(view, input, now, env)` 对同一输入 + 同一视图永远得到同一批事实；
- 判断、事实追加、`evolve` 更新投影在 **SQLite WAL + FULL 的同一个事务**里完成，提交后才应答；
- 200000 步固定种子模拟、1000 次真进程 SIGKILL、31 处变异检查都建立在这个确定性上。

一旦内核里调用 DeepSeek，这几条全破：回放会重新烧 token、结果不可复现、崩溃恢复无法重放。

`dsh-superagent-prototype` 的答案是「Main Session 评估」：一个叫 `orchestrator` 的主会话，通过 `orchestrator_eval` / `orchestrator_eval_read` / `orchestrator_eval_decide` 三个工具，对**推断型（inferred）候选**做研判；`src/app/assessment.ts` 的 `MasterAssessor` 把候选卡片送进主会话，`src/policy.ts` 的 `assessmentOutcome()` 把模型回答转成 `Engine.decide()` 的 outcome。它的关键设计是：**Gate 是确定性代码，Assessment 才是模型**，而且 Decision 落库后不再重跑。

移植结论：

```
事实日志 ──SSE/订阅──▶ Assessor 插件（host 层，出网，调用 DeepSeek）
                          │  eval.decided 命令（含 policy_version / reasons / evidence）
                          ▼
                    commit() 写一条事实 ──▶ evolve() 更新投影 ──▶ 派活 / 忽略
```

- 评估结论连同 `policy_version` 与 `reason.code` 作为一条 `eval.decided` 事实落日志；按 master 决策，**不记录模型调用明细、不做 DeepSeek 专项审计**。
- 回放只重放事实，不重跑模型；若要「换个模型会怎么判」，用 **fork 分支 + what-if 重评估**，不污染主分支。
- 评估器可整体关闭：`eval.enabled: false` 时退化为纯 Gate + 规则路由，即原版 agent-autoloop 行为。这就是「审批卡片可配置开关」的同一套策略机制。

### 0.2 审批卡片能不能做成配置开关？

**能，且应该做成 Policy 的一个版本化字段，而不是代码分支。**

底座已有两个半成品：`rules.json` 的 `askFirst: [...]`（哪几类事必须先问）与 `tell: always|needed|never`（通知强度），回执 `ask` 会生成带选项的卡片并让本轮退出（挂起零消耗）。dsh 侧有 `Attention`（工单上等人回答的结构化问题）与 `Delivery requirements`（合并前要审批）的约定。

统一成一个 `ApprovalGate` 纯函数（模板见 `src/kernel/approval.ts`）：

| mode | 行为 | 是否阻断 | 是否发卡 | 适用场景 |
| --- | --- | --- | --- | --- |
| `off` | 按规则直接放行，仅记 `approval.auto` 事实 | 否 | 否 | 本地只读任务、已充分验证的巡检 |
| `notify` | 放行 + 一张 `fyi` 灰卡（不带按钮、不进 open） | 否 | 是（低成本） | 想留痕但不想被打断 |
| `gate` | 挂起本轮，发带选项卡片，回答是新的 `card.answered` 事件 | 是 | 是 | 删数据、停服、花钱、对外发消息、合并 |
| `escalate` | 先按规则自动尝试 N 次 / 或评估置信度低于阈值时才升为 `gate` | 条件 | 条件 | 告警自愈、重试后仍失败 |

开关粒度：`全局 → 项目 → 规则 → 动作类别` 四级覆盖；任何一次修改都写 `policy.changed` 事实并带上新 `policy_version`，影响在途 Mandate 的复验（见 `docs/03`）。

### 0.3 怎么做到「占用最少的人的注意力」

把它从口号变成**可度量的预算**，这是两个仓库共同理念里最值得移植的一条（`docs/000-philosophy.md`：「Take as little human attention as possible」；底座 `docs/protocol.md` 六原则第 1 条「注意力最贵，默认安静」）。

| 机制 | 实现组件 | 度量 |
| --- | --- | --- |
| 默认安静 | `tell: needed`、`quiet` 卡片、`fyi` 通知 | 每轮是否产生卡片 |
| 只在必须时说话 | dsh「只在人必须行动或可用到结果时开口」 | 卡片中 `actionable` 占比 |
| 一次只问一个具体问题 | `ask` 结构化选项、同一 `key` 未关闭不重复问 | 单卡选项数、重复问次数 |
| 挂起零消耗 | 问完即退出进程，状态只在 SQLite，回答事件唤醒 | 等待期间进程数 / Token |
| 合并与去重 | 同 `source+id` 去重、同 `key` 卡片去重、`notify once` | 重复通知数 |
| 健康状态不占版面 | dsh 面板原则「A healthy state takes no space」 | 仪表盘红色区块数 |
| 噪声熔断 | 单位时间卡片上限、冷却窗口、超量自动降级成摘要 | `cards/person/hour` |
| 一次性瞬时错误不打扰 | 连续 3 次失败才升级为系统问题（dsh Effects / 底座失败表） | 误报率 |

**注意力预算**写进配置：`attention.maxCardsPerHour`、`maxQuestionsPerTicket`、`digestAfter`，超限后把多张卡片合成一张摘要卡，并自动把该项目临时降为 `notify`。这是「自激防线」在人机接口上的延伸。

## 2. 分层与组件

### 2.1 六层

```
┌──────────────────────────────────────────────────────────────────┐
│ L5 运维与观测   Watchdog · HealthBoard · Audit · AttentionBudget   │  只观测/自愈/升级
├──────────────────────────────────────────────────────────────────┤
│ L4 交互与后台   Cards(飞书/桌面) · Dashboard · Blackboard · CLI/MCP │  只呈现/收回答
├──────────────────────────────────────────────────────────────────┤
│ L3 执行与能力   Worker · Agent 插件 · ExecutionEnvironment · Skills │  跑一轮，交回执
├──────────────────────────────────────────────────────────────────┤
│ L2 领域与编排   Intake · Gate · Assessor · Router · Ticket/Grant    │  决定五问，产出事实
│                  · ApprovalGate · Outbox · Effects                  │
├──────────────────────────────────────────────────────────────────┤
│ L1 运行外壳     HTTP · SQLite · 时钟 · 配置 · 插件加载 · 服务托管   │  唯一有 I/O 的一层
├──────────────────────────────────────────────────────────────────┤
│ L0 确定性内核   decide() · Fact Log · evolve() · View · due/        │  零 I/O、零时钟、零随机
└──────────────────────────────────────────────────────────────────┘
```

依赖规则（移植 dsh `docs/007-architecture.md` 的「Dependency rules」）：

1. **L0 不 import 任何 L1+ 代码**，只用 `node:` 的哈希；`decide` 与 `evolve` 都是纯函数。
2. **L2 只通过端口（ports）访问 L1**：`Repositories`、`Policy`、`SourceScope`、`Assessor`、`Executor`、`Outbox`、`Effects`、`Clock`。
3. **每个调用方只拿到自己角色需要的 `Pick<Engine>`**：`EngineForSources` / `EngineForMainSession` / `EngineForPeople` / `EngineForSettings` / `EngineForExecutor`（模板见 `src/domain/ports.ts`）。
4. **一个状态一个写者**：事实日志 → `commit`；投影 → `evolve`；健康条目 → 认领它的组件；设置与提示词 → `Settings` / `Prompts`；Outbox 回执 → `Outbox`。
5. **命令与事实命名**：请求用祈使动词（`stopTicket`），适配器上报用过去式（`assignmentStarted`、`cardDelivered`）。

## 3. 五问：从一件事到一条闭环

```
[定时 / Webhook / 轮询 / 飞书]  ──▶ ① 什么事：Trigger 归一化
        │  trigger.received (taint=external, hops=0, policy_version=P7)
        ▼
② 做不做：Gate ──(explicit 直接路由)──┐
        │ inferred / 需研判           │
        ▼                            │
   Assessor（主会话 LLM，可关）       │
        │ eval.decided{accept|ignore}│
        ▼                            │
   Grant（Mandate，记录 P7 与匹配规则）◀┘
        │ ticket.created
        ▼
③ 给谁做：Router → agent 能力 / 容量 / 会话 / 并发槽
④ 在哪做：project + cwd + worktree + access(read|edit|full)
        │ assignment.started
        ▼
⑤ 怎么做：Skill/Prompt → Agent 一轮 → 回执(ask/notice/resolve/later/events)
        │ run.result（回执在一个事务里一次生效）
        ▼
   副作用闸门：approval / emits 白名单 / hops+1 / 预算
        │
        ├── 可以自动闭环 ─▶ 完成 / later 复查 / resolve 结案
        └── 必须人行动   ─▶ 卡片 → 进程退出（挂起零消耗）→ 回答事件 → 原会话续接
```

每一步都产生事实，事实带 `causation_id` / `correlation_id`，因此「为什么跑」可被完整还原。对应到用户五问的组件与产出：

| 问题 | 组件 | 输入 | 决策依据（不可被外部文字篡改） | 产出事实 |
| --- | --- | --- | --- | --- |
| 什么事 | `Intake` | 原始 payload | `source` 配置 + schema 校验 + taint 标记 | `trigger.received` |
| 做不做 | `Gate` + `Assessor` | Trigger 批次 + Thread 快照 + Policy | `policy.json` 版本、准入表、接受模式 `off/observe/auto` | `eval.started`、`eval.decided` |
| 给谁做 | `Router` | Decision + 能力表 | `rules.json` 的 `to`、worker capacity、会话可用性 | `ticket.created`、`run.queued` |
| 在哪做 | `ExecutionEnvironment` | Ticket + 项目 | `projects[].cwd`、`access`、worktree 白名单 | `assignment.started` |
| 怎么做 | `Receipt` + `ApprovalGate` | Agent 最后一轮输出 | `emits` 白名单、Skill、审批策略 | `run.result`、`card.created`、`timer.scheduled` |

> **边界**：外部文字（Issue 正文、飞书消息、网页内容）只能成为 Trigger 的 `summary/detail`，打 `taint: external`，写进标注「这是资料」的 `contextFile`。它**不能**决定 `to / cwd / skill / access / emits / 收件人`。这是底座「规则才是指令」与 dsh「Outside text is data」两条原则的合流。

## 4. 端到端示例：一条 GitHub Issue 到合并前审批

| # | 事实 type | 关键字段 | 谁写的 |
| --- | --- | --- | --- |
| 1 | `trigger.received` | `source=github, project=home-deco, type=issues.opened, taint=external, hops=0` | Intake |
| 2 | `eval.started` | `strength=inferred, policy_version=P7, mode=observe` | Gate |
| 3 | `eval.decided` | `outcome=ignore, reason=would_accept, policy_version=P7` | Assessor（`observe` 模式只记录不接单） |
| 4 | `policy.changed` | `P7→P8, mode=auto, changed=[acceptMode]` | 人在面板改配置 |
| 5 | `trigger.requeued` | 同一 Trigger 用 P8 重新评估 | 内核 |
| 6 | `eval.decided` | `outcome=accept, matched_rules=[issue-triage], intent_evidence=...` | Assessor |
| 7 | `grant.created` | `mandate: scope, strength, basis, policy_version=P8` | GrantLedger |
| 8 | `ticket.created` / `assignment.started` | `agent=codex, cwd=~/code/home-deco, access=edit` | Router |
| 9 | `run.result` | `outcome=done, ask=[{title:"是否合并 PR #42", options:[合并,先不]}], events=[pr.merged?]` | Worker |
| 10 | `approval.required` | `action=merge, mode=gate, category=对外发消息` | ApprovalGate |
| 11 | `card.created` | 飞书卡片，带按钮与 `answerers` 白名单 | Channel |
| 12 | — **进程退出、零 Token、零轮询** — | 状态全在 SQLite | 挂起 |
| 13 | `card.answered` | `choice=合并, by=ou_xxx, ref=om_xxx, hops 不清零` | Channel 回调 |
| 14 | `grant.revalidated` | 用当前 P8 复验 Mandate 是否仍成立 | GrantLedger |
| 15 | `run.queued` | 接原会话续接，只做剩余步骤 | 内核 |
| 16 | `audit.trace` | 一键给出 1–15 全链路 | Audit |

## 5. ADR：关键设计决策

| # | 决策 | 理由 | 代价 / 风险 |
| --- | --- | --- | --- |
| ADR-1 | fork 底座，全部扩展为**增量**，不改 `/v1` 已有语义 | 底座明确承诺兼容性；老规则、老插件、老客户端必须继续能跑 | 新字段只能可选，协议会变胖 |
| ADR-2 | dsh 的领域模型**重表达为事实投影**，不搬它的 `Engine`/`Store` | 两个仓各有一套 SQLite 状态；双写必然不一致。以底座的单条事实日志为唯一真相 | 移植工作量比直接复制大 |
| ADR-3 | LLM 只存在于 `host/Assessor`，结论以事实回写 | 保住内核确定性与崩溃重放 | 评估有延迟，需要 Eval 超时/重试/`unavailable` 语义 |
| ADR-4 | Gate 确定性在前，Assessment 只在 inferred/必要时候调用 | dsh 原设计；省 token、可审计、防注入 | 显式请求不走模型，可能少一层理解 |
| ADR-5 | 审批策略是版本化 Policy 字段，不是代码开关 | 可回放、可复验、可撤销、可灰度（observe→auto） | 策略变更要广播给在途 Ticket |
| ADR-6 | 一切挂起事件化，唤醒前强制复验 Mandate | 授权可撤销的落点；底座已证明挂起零消耗 | 复验失败要回退成新 Eval，逻辑要写全 |
| ADR-7 | fork/断点只在**分支日志**上生效，生产分支只读 | 断点会破坏生产确定性；调试/审计不应影响真实工作 | 分支日志占磁盘，需要 GC 策略 |
| ADR-8 | 多项目用 `project_id` 命名空间隔离，不启多实例 | 一台电脑一个中台（底座前提），实例多则密钥/端口/服务都翻倍 | 需要严格保证跨项目读写隔离 |
| ADR-9 | 交付**可交互前端**，但仍只消费预留接口、不新增后端写路径 | master 拍板「要出可交互前端」；dsh 面板绑定 DSH 宿主，不能搬 | 前端是独立静态工程，后端未启动时用演示数据，需明确标注 |
| ADR-10 | Watchdog 自身也受自激防线与注意力预算约束 | 自愈循环是最典型的自激源 | 自愈失败最终仍要一张卡找人 |
| ADR-11 | **不做「审计追踪 DeepSeek」**：不记模型调用明细、不让模型生成审计摘要 | master 拍板；通用因果链已能回答「为什么跑、谁批的、依据哪版策略」 | 少一层状态与噪声；评估器仍可用、可关、可回放 |
| ADR-12 | 生产只听本机 `/v1`，飞书回调走反向代理 + `publicUrl` | 底座安全边界；不开公网端口 | macOS 上要配 HTTPS 反代或隧道 |
