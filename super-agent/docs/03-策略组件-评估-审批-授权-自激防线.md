# 03 策略组件：评估 / 审批 / 授权 / 自激防线

> 本文是「做不做、谁批、批到哪、会不会自己把自己转爆」的规则总集。
> 所有策略都是**版本化配置**，每次变更写 `policy.changed` 事实；所有判定函数在 `kernel/` 是纯函数。

---

## 1. Policy：一个版本串起全部规则

`config/policy.json`（示例全量见 `config/rules.example.json` 的 `super` 段）：

```jsonc
{
  "policy_version": "P8",              // 由内容哈希自动计算，不接受手填
  "accept_mode": "observe",            // off | observe | auto（移植 dsh）
  "admission": {                        // 每个 Source 一张准入表
    "github": {
      "allowed_senders": ["gao", "reviewer-bot"],
      "bots": ["dependabot[bot]"],
      "scopes": {
        "issues.opened": { "listed_unaddressed": "inferred", "unlisted_addressed": "ignore", "unlisted_unaddressed": "ignore" },
        "issue_comment":  { "listed_unaddressed": "inferred", "unlisted_addressed": "explicit", "unlisted_unaddressed": "ignore" }
      }
    }
  },
  "rules": [
    { "id": "issue-triage", "name": "处理新 Issue", "instruction": "只做分类与复现，不推送、不合并", "enabled": true },
    { "id": "ops-alert",    "name": "线上告警排查", "instruction": "先读日志定位；重启需审批", "enabled": true }
  ],
  "eval": {
    "enabled": true,
    "provider": "deepseek",
    "model": "deepseek-chat",
    "timeout_ms": 120000,
    "max_retries": 2,                  // 第三次超时记 unavailable
    "context_budget": { "trigger_chars": 4000, "near_chars": 1200, "window_chars": 400, "max_messages": 11 },
    "reassess_on_policy_change": true
  },
  "approval": { /* 见 §3 */ },
  "attention": { /* 见 §7 */ },
  "excitation": { /* 见 §6 */ },
  "grants": { /* 见 §4 */ }
}
```

`policy_version` 哈希覆盖：`rules` + `accept_mode` + 各 Source 的 `admission` + `approval` + `attention` + `excitation` 关键阈值。任何变化都：

1. 写 `policy.changed{from,to,changed_paths}` 事实；
2. 丢弃在途 Eval，把其 Trigger 用新版重排（dsh `Engine.policyChanged` 语义）；
3. 给受影响的活跃 Ticket 发一条 `policy_changed` Input（**只通知，不立即撤销**）；
4. 唤醒/续接时按新版**复验** Mandate（见 §4）。

配置保存沿用 dsh `Settings.save(block, value, baseRevision, origin)`：带 `origin = panel|tool|sync`，CAS 冲突拒绝，历史版本不可变。

## 2. 主会话 LLM 评估（能否支持 → 怎么支持）

### 2.1 两层 Eval

```
Trigger 批次 ──▶ Gate（内核纯函数，确定性）
                   ├─ not admitted ─▶ trigger.filtered（只记录）
                   ├─ explicit     ─▶ 直接路由，不调模型
                   └─ inferred     ─▶ 需要 Assessment（旁路插件）
                                        │ eval.decided
                                        ▼
                              accept|ignore|unavailable
```

| 概念 | 取值 | 来源 |
| --- | --- | --- |
| `strength` | `explicit` / `inferred` / `not_admitted` | dsh `docs/002-authorization.md` |
| `accept_mode` | `off` / `observe` / `auto` | dsh，默认 `observe` |
| `decision` | `accept` / `ignore` / `stop` / `unavailable` | dsh + 底座 outcome |
| `reason.code` | `would_accept` / `no_matching_rule` / `matched_rule` / `timeout` / `policy_changed` / `said` | dsh `src/core/reasons.ts` |

**最小注意力落点**：`observe` 模式下，模型判断「本来会接」时**只记 `ignore + would_accept`，不接单、不发消息**。人在 Blackboard 的「本来会接」泳道看过一批之后再切 `auto`。这是从 dsh 搬来的最实用一条。

### 2.2 Assessor 组件（host 层，唯一出网做研判的地方）

```ts
// src/host/assessor.ts（模板）
interface AssessorPort {
  // Effect kind = "assessment"，先存后做；(kind,key) 合并，Later 不计失败
  request(candidate: Candidate): void;      // 引擎在事务内 enqueue
  deliver(evalId: string, card: CandidateCard): Promise<void>;  // 送达主会话后才开始计时
  decide(evalId: string, outcome: AssessmentOutcome): void;     // 命令写回 eval.decided
  release(evalId: string): void;            // 释放上下文缓存
}
```

关键约定（照搬 `MasterAssessor`）：

- **超时从「候选卡送达主会话」开始算**，不是从入队开始；未送达的候选永不过期。
- 连续 2 次超时重排，第 3 次记 `unavailable`；模型/网络瞬时失败（408/429/5xx）走 3 次指数退避。
- 主会话**不等待**：报告、追问、候选、后台任务都作为消息自动到达，`noWait` 守卫拒绝 `sleep`、超过 30s 的 shell timeout 与超过 5s 的 job wait。
- 上下文有界：Trigger 4000 字、近邻 1200 字、窗口 400 字、其余 50 字 stub；`orchestrator_eval_read` 按 id 展开；避免把整个仓库/整个群历史塞进上下文。
- 每条启用的规则**恰好评估一次**（无论是否匹配）；`auto` 模式下 `accept` 必须至少匹配一条规则并给出 `intent_evidence`。
- 显式请求不走评估，直接 `route`；一次 `route` 可含 1–20 个决定，单项失败不影响其它项。

### 2.3 与内核的边界（红线）

| Assessor 能做 | Assessor 不能做 |
| --- | --- |
| 读 Thread 窗口、读仓库受限路径、产出 `decision + reason` | 直接写投影、直接发事件、直接起 Agent |
| 通过命令把结论作为一条事实写回 | 修改 `rules.json` / `policy.json`（只有面板能改执行环境与 SETUP 字段） |
| 记录 `policy_version` 与 `reason` | 决定 `to/cwd/access/emits/收件人` |

结论是**一条事实**，因此：回放不重跑模型；换模型用 fork what-if；策略版本不一致的结论记 `unavailable` 并重排。按 master 决策，不做模型调用明细记录、不做 DeepSeek 专项审计；超时与失败仍记 `unavailable` 事实并进 HealthBoard。

## 3. 审批卡片：配置开关

### 3.1 配置

```jsonc
"approval": {
  "enabled": true,
  "default_mode": "gate",                 // off | notify | gate | escalate
  "categories": {
    "delete":        { "mode": "gate" },
    "restart":       { "mode": "gate" },
    "spend":         { "mode": "gate", "threshold_usd": 0 },
    "external_message": { "mode": "gate" },
    "merge":         { "mode": "escalate", "after_auto_attempts": 2 },
    "read_only":     { "mode": "off" },
    "routine":       { "mode": "notify" }
  },
  "overrides": [
    { "project": "home-deco", "rule": "ops-alert", "category": "restart", "mode": "off",
      "reason": "已通过 runbook 固化，且只作用于隔离环境" }
  ],
  "answerers": ["ou_xxx"],              // 谁能拍板（飞书通道），多项目按项目隔离
  "channels": ["feishu", "desktop"],
  "timeout_hours": 24,
  "on_timeout": "deny",                 // deny | escalate | auto（默认 deny，绝不默认放行）
  "one_question_at_a_time": true,
  "revocable": true
}
```

四级覆盖：`全局 default_mode → category → project → rule`。解析是内核纯函数，结果连同 `policy_version` 记在 `approval.*` 事实里。

### 3.2 四种模式的语义

| mode | 是否阻断本轮 | 卡片形态 | 回答事件 | 挂起零消耗 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| `off` | 否 | 无 | 无 | — | 只读巡检、已固化 runbook |
| `notify` | 否 | `fyi` 灰卡，创建即 closed，不带按钮 | 不产生 | — | 想留痕不打断 |
| `gate` | 是 | 带选项卡片（`ask`），写 `approval.required` | `card.answered` → `approval.granted/denied` | 是 | 删数据、停服、花钱、对外发消息 |
| `escalate` | 条件 | 前 N 次自动处理，超阈值/评估置信度低才升为 `gate` | 同上 | 是 | 告警自愈、合并前审批 |

实现要点：

- `ask.key` 作用域是「事项」：同一 key 的卡片还开着就不重复发（底座 `kernel/decide.ts:218`）。
- 问完**本轮立即结束**，进程退出、不占 Token；回答是 `card.answered` 事件，`hops` 不清零，回到提问时的事项并尽量接原会话。
- 卡片超时 `on_timeout: deny`：写 `approval.expired`，事项按「未获授权」处理，**不静默放行**。
- `revocable: true`：已批准但尚未执行的动作，可被 `grant.revoked` 撤回；执行前最后一次复验。
- 底座 `askFirst` / `tell` 继续生效，作为旧配置的兼容层：`askFirst` 命中 → 强制 `gate`；`tell: never` → 压制通知卡片但不压制提问与安全告警。

### 3.3 飞书卡片

沿用底座 `plugins/feishu/channel.ts` 协议：`GET /v1/cards/next` 长轮询、`POST /v1/cards/:id/delivered{version,ref}`、`POST /v1/cards/:id/failed`、`POST /v1/cards/:id/answer{choice,by,ref}`。

| 要求 | 做法 |
| --- | --- |
| 谁能答 | `channels[].answerers` 白名单；`by` 必须在名单内；`ref` 必须与送达那条一致；只有第一次算数 |
| 幂等 | 发新消息只用卡片编号不带版本；更新用 `ref+version`；飞书改不动已结束卡片时另发一条并带版本 |
| 送达失败 | 递增退避重试，1 小时后放弃但卡片仍开；`fyi` 通知创建后 24 小时内仍可投递 |
| 不重复打扰 | 未送达就已解决的卡片不再投递；同一阻塞已有 open 卡片时不重复问；同一 `key` 的 `waiting` 复查用 `cancel` 取消 |
| 手机可批 | `hub.publicUrl` 配成手机可打开的 HTTPS 地址（反代），中台本体仍只听本机 |
| 链接兜底 | 只有配 `links: true` 的通道用链接回答；**持有即授权**、7 天有效，绝不发到公开位置 |
| 多项目 | 卡片带 `project_id` 标签；不同项目可配不同 `answerers` 与群 |

## 4. 挂起零消耗 + 授权可撤销

### 4.1 挂起零消耗（底座原生，保留）

```
Agent 回执 ask ─▶ 本轮 done 并退出 ─▶ 卡片状态存 SQLite ─▶ 无进程 / 无 Token / 无轮询
        ▲                                                        │
        └──────────── card.answered 事件唤醒 ─── 接原会话继续 ◀────┘
```

底座事实：等待三天，这三天没有 Agent 进程在跑、不花 Token，只有很轻的中台在后台；回答后接原会话。到期复查（`later`）、重试、租约、离线判断共用 `due` 表，外壳只安排**下一次到期**的定时器——不是轮询。

### 4.2 授权（移植 dsh Mandate）

```ts
interface Grant {
  id: string;
  ticket_id: string;
  project_id: string;
  policy_version: string;       // 接单当时的版本
  scope: string;                // 允许做到哪
  strength: "explicit" | "inferred";
  basis: "addressed" | "followup" | "admission" | "bot";
  matched_rules: string[];
  source: string; scope_row: string; sender: string;
  state: "active" | "revoked" | "withdrawn";
  created_at: number; revoked_at?: number; revoke_reason?: string;
}
```

**只有三种操作改变 Grant**（照搬 dsh `docs/002`）：

| 操作 | 事实 | 效果 |
| --- | --- | --- |
| `accept` 创建 | `grant.created` | 记录当时 Policy 版本与依据 |
| 人 `stop` 撤回 | `grant.revoked{reason:"manual_stop"}` | 立即失效，Ticket 终结且不再接收消息 |
| 复验失败撤销 | `grant.revoked{reason:"revalidation_failed"}` | 结束态 Ticket 保持结束；等待的消息回退到新 Eval |

策略变更**不立即撤销**在途 Grant，只发 `policy_changed` Input；复验在唤醒时做（避免半截工作被取消，dsh `docs/001`「Rejected concepts」）。

### 4.3 复验矩阵（唤醒前必做）

| Grant basis | 复验条件 |
| --- | --- |
| `addressed`（名单内的人明确 @） | Source 仍监听该 Thread 即通过 |
| `followup`（已有 Ticket 的 Thread 上的追问） | 同上；显式追问直接通过 |
| `admission`（准入表单元格） | 当前表仍给至少原强度；发送人仍在名单；`inferred` 还需 `auto` + 匹配规则仍启用 |
| `bot` | bot 仍在 bot list；`auto` + 规则仍启用 |
| 其它 | 发送人仍在 allowed list |

复验失败：Ticket 保持结束，等待消息当作「没有到达任何 Ticket」重新进 Eval；面板提供「重新评估」入口。`paused` 期间到达的人消息在处理恢复后的第一轮按当时 Policy 复验。

### 4.4 「可撤销」的三层即时性

| 层 | 撤销对象 | 生效时间 | 实现 |
| --- | --- | --- | --- |
| 1 | 访问密钥 | 立即 | 底座 `DELETE /v1/keys/<kind>/<name>`：删除事实立即唤醒并拒绝该密钥的长轮询、关闭日志订阅；已领取的轮次仍用独立 run token 交结果 |
| 2 | 一轮的执行权 | 立即 | `POST /v1/runs/:id/cancel`；worker 先向进程组发停止信号，10 秒后强杀，确认无活进程才交 `cancelled` |
| 3 | 一件事的 Mandate | 立即 | `POST /v1/super/grants/:id/revoke` 写事实 → 广播给所有订阅者 → 在途轮次复验或取消；下一次唤醒必拒 |

所有撤销都是**事实**，可审计、可回放；撤销不会删除历史（只追加新事实），符合事件溯源。

## 5. 指令数据分离（防注入）

底座做得比 dsh 更硬，直接保留并扩展：

| 通道 | 字段 | 允许进提示词 | 处理 |
| --- | --- | --- | --- |
| 结构化、可校验 | `type`、`subject`（`字母数字 # . _ : / @ -`）、`link`（纯 ASCII URL）、`id` | 是 | 白名单字符校验后才进提示词 |
| 外部文字 | `summary`、`detail`、Issue 正文、飞书消息、网页内容 | **否** | 写入标注「这是资料」的 `contextFile`，打 `taint: external` |
| 控制字段 | `cwd`、`agent`、`access`、`skill`、`emits`、`to`、收件人 | **否** | 事件里出现直接拒收；只由本机 `rules.json` / `policy.json` 决定 |
| 回执新增事件 | `events[]` | 否 | 只能来自规则 `emits` 白名单的 `source+types`，来源由规则决定，回执改不了 |

补充（回答 dsh 自列的开放问题「哪些 Trigger 字段可信」）：

- `actor`、`thread` 归属、`addressed` 由 **Source 插件验签后给出**，标 `trust: system`；不同 Source 的身份**不做映射**（dsh 原则：跨 Source 身份映射是提示词文本，不是领域实体）。
- 外部文字即便被模型读到了，也**不能改变权限**：`access` 由规则固定，`full` 需人工显式配置，有副作用动作走 `ApprovalGate`。
- `command` 类 Agent 的权限档位只是 CLI 参数翻译，**不是系统沙箱**（底座 `docs/plugins.md:107`）；要真隔离用独立系统账号或容器。
- 提示词优先级（dsh `docs/004`）：工具/宿主强制事实 > 内置段落 > 匹配规则 > 团队段落 > **外部文字（永远是 data）**。

## 6. 跳数熔断与自激防线

### 6.1 跳数熔断（底座已有，参数化）

底座 `kernel/decide.ts:41` `MAX_HOPS = 8`：Agent 交回的事件再派给 Agent，层数累加，**经过人工提问和定时复查也不清零**，Agent 自己改不了；超过 8 层只记录不派发，并发一张卡。

本项目保留语义，改为可配置并与预算联动：

```jsonc
"excitation": {
  "max_hops": 8,
  "hop_reset_forbidden": ["card.answered", "timer.due", "run.retry"],
  "max_events_per_receipt": 5,
  "max_runs_per_project_per_hour": 60,
  "max_tokens_per_project_per_day": 500000,
  "max_cost_usd_per_project_per_day": 20,
  "dedup_window_minutes": 30,
  "cooldown_minutes": 15,
  "on_trip": "record_and_notify"     // record_and_notify | silent
}
```

### 6.2 五层自激防线

| 层 | 防的是什么 | 机制 | 事实 |
| --- | --- | --- | --- |
| L1 入口 | 外部文字变成指令、事件自带派活参数 | 字段白名单 + taint + `emits` 白名单 + 拒收控制字段 | `trigger.filtered` |
| L2 因果 | Agent → 事件 → Agent 无限回环 | `hops` 单调不清零、`(source,type,subject)` 因果环检测、同 `digest` 去重 | `run.result`、`excitation.tripped` |
| L3 预算 | 高频自触发烧钱/刷屏 | 每轮事件数、每小时轮数、每项目每日 token/费用上限；超限**记录不派发** | `excitation.tripped` |
| L4 冷却 | 熔断边缘反复试探 | 命中后 `cooldown_minutes` 内同源同型事件合并成一条摘要；`notify once` 保证只发一张卡 | `health.changed` |
| L5 人工 | 前四层都没挡住 | 一张「事件循环已停止」卡片 + Blackboard 红色泳道；恢复需人显式操作或冷却到期自动降级 | `card.created` |

**关键**：熔断之后不是静默丢弃——底座做法是「仍记录、不派发、发一张卡」，保证可审计；但卡片只有一张（`once: true`），避免熔断本身变成新的噪声源。

### 6.3 Watchdog 自身也在防线内

自愈重启 → 又失败 → 又重启 是最典型的自激。Watchdog 有独立的 `self_heal_budget`（每小时每组件最多 N 次），超限后停止自动重启、降级为「组件停用 + 一张卡」，见 `docs/04`。

## 7. 注意力预算（把理念变成可执行约束）

```jsonc
"attention": {
  "max_cards_per_owner_per_hour": 4,
  "max_questions_per_ticket": 2,
  "max_words_per_card": 100,
  "digest_after": 3,                  // 超过 3 张/小时合并成一张摘要卡
  "quiet_hours": "23:00-08:00",      // 非紧急卡片延迟到窗口外合并投递
  "escalate_only_when_actionable": true,
  "suppress_transient_errors": 3,    // 连续 3 次失败才升级为系统问题
  "healthy_state_takes_no_space": true
}
```

| 执行点 | 行为 |
| --- | --- |
| `ApprovalGate` | `off/notify` 优先，能不打断就不打断 |
| `createCard` | 同 `key` 未关闭不重复发；`fyi` 不带按钮；一次只问一个具体问题 |
| `notify once` | 同一告警 `digest` 只发一次 |
| 汇总 | 超限后把多张卡合成一张摘要，并临时把该项目降为 `notify` |
| Blackboard/仪表盘 | 健康区块折叠；只有「需要人」的泳道默认展开 |
| Watchdog | 一次性网络错误不打扰，连续 3 次才升级 |

度量指标：`cards/owner/hour`、`questions/ticket`、`attention words/day`、`actionable ratio`、等待期间 `active_agent_processes = 0`。全部从事实 `meta.attention_cost` 聚合，可在仪表盘查。

## 8. 定时 / Webhook / 多项目 / 飞书卡片

| 能力 | 实现 | 底座依据 |
| --- | --- | --- |
| 定时 | `when.cron`；错过的只补最近一次；夏令时重复时刻只跑第一次、不存在的时刻跳过 | `kernel/cron.ts`、`docs/protocol.md:84` |
| Webhook | `POST /v1/in/<source>`，插件 `source.ts` 只做验签 + 翻译、不发请求；密钥在 `secrets.env` 的 `AGENT_AUTOLOOP_SECRET_<SOURCE>` | `docs/plugins.md:89` |
| 轮询 | 定时脚本作为 Agent，回执 `events` 交回新事件，`id` 稳定、范围可重叠、中台去重；游标只在回执交出后推进 | `docs/protocol.md:86` |
| 多项目 | 所有事实带 `project_id`；`projects[]` 各自 `cwd / rules / policy / keys / budgets / worker capacity / answerers`；单中台单端口，不启多实例；跨项目读写强制带命名空间 | **本次新增**（底座明确无多租户） |
| 飞书卡片 | 见 §3.3；按钮回调、身份由平台核验、`answerers` 白名单 | `plugins/feishu/channel.ts` |
| 交付流水线 | `plugins/delivery` 继续作为普通 Agent 插件，内核不认识它 | `docs/protocol.md:391` |

多项目隔离检查表：

- [ ] 事件必须带 `project_id`，缺省 `default`；来源密钥与项目绑定，不能冒充别的项目。
- [ ] `cwd/worktree` 只能取 `projects[id].cwd` 下的路径，符号链接要核对（底座 ACP 权限做法）。
- [ ] 每个项目独立 `attention` / `excitation` 预算与 `answerers`。
- [ ] Blackboard 按项目分泳道；`GET /v1/state` 兼容旧格式，新字段可选。
- [ ] 备份/恢复按项目可导出；审计可跨项目但默认按项目过滤。
